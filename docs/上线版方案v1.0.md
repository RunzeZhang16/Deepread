## 一、C 端和 B 端网址不一样吗？

**同一个主域，不同入口。**

```
www.deepread.com           C 端主站（免费，做口碑和获客）
www.deepread.com/pro       B 端落地页（介绍行业日报，留资/下单）
mail.deepread.com          邮件发送域（提高送达率）
```

B 端**不靠网页交付**，靠邮件交付：

```
每天 7:30 → 邮件推送到客户邮箱 → 点标题跳原文
```

**为什么不给 B 端单独域名：**

- 域名、SSL、备案、SEO 全部翻倍
- 品牌分裂，客户不知道你是不是同一家
- 你一个人维护不过来

**唯一要分开的是"落地页"**：C 端首页是内容流，B 端 `/pro` 是销售页（样刊、定价、留资表单）。

## 二、要不要做成 App？

**不要。至少一年内不要。**

理由很实在：

| 渠道 | 获客成本 | 留存 | 你的维护成本 |
|---|---|---|---|
| **网页（移动端适配）** | 最低，链接就能发 | 中 | 低 |
| **邮件** | 0（已有订阅者） | **高**（每天必达） | 低 |
| **微信公众号** | 低，靠内容涨粉 | 高 | 中 |
| **微信小程序** | 中 | 高 | 中 |
| **原生 App** | **最高**（应用商店+下载） | 高 | **高**（双端+审核+发版） |

一个日更内容产品，**用户每天只需要看 10 分钟**——这种使用频次撑不起一个 App 的下载门槛。

**正确顺序：**

```
第 1 阶段：响应式网页 + 邮件        ← 现在
第 2 阶段：微信公众号（内容引流）    ← 有 100 个订阅者后
第 3 阶段：小程序（可选）            ← 有稳定收入后
第 4 阶段：App                      ← 大概率永远不需要
```

## 三、正式上线部署到哪里？

### 3.1 三条路的取舍

| 方案 | 备案 | 成本 | 优点 | 缺点 |
|---|---|---|---|---|
| **A. 香港轻量服务器** | ❌ 免 | 24–40 元/月 | 立刻能用、无中间页 | 速度一般，理论上有被墙风险（概率低） |
| **B. 国内云 + 备案** | ✅ 2–4 周 | 24–60 元/月 + 域名 | 速度最好、合规 | 备案要等，还要挂网站负责人 |
| **C. 腾讯云 CloudBase** | 默认域名有中间页 | 按量 | 已跑通 | 中间页 + 冷启动，不适合正式上线 |

### 3.2 推荐路径

```
现在 → 香港轻量服务器（A），一周内上线
6 个月后，有稳定收入 → 迁国内 + 备案（B）
```

**香港服务器具体配置：**

```
2 核 2G / 40G SSD / 30Mbps 峰值
Ubuntu 22.04
Docker + docker-compose
Nginx 反代 + Let's Encrypt 免费证书
```

⚠️ 注意：**不要买太便宜的"香港虚拟主机"**，要能跑 Docker 的轻量 VPS（腾讯云国际站、阿里云国际、Vultr、BandwagonHost 都行）。

### 3.3 域名与备案

- 域名：`.com` 约 70 元/年（阿里云/腾讯云注册）
- 香港服务器**不需要备案**，解析直接生效
- 如果域名在国内注册商，解析到境外 IP 通常也没问题

## 四、大模型怎么用？（最关键的工程决策）

### 4.1 三个调用点

| 场景 | 频率 | 模型 | 单次成本 |
|---|---|---|---|
| 摘要 + 问题生成 | 每天 10–12 次 | DeepSeek-Flash | ~0.01 元 |
| 候选打分 | 每天 100 条（批量） | DeepSeek-Flash（低推理档） | ~0.0003 元/条 |
| 用户对话 | 每人每天 1–3 轮 | DeepSeek-Flash | ~0.01 元/轮 |

### 4.2 架构原则

```
浏览器 → 你的服务器 → DeepSeek API
         ↑
    key 只存在服务器环境变量里
```

**四条硬规则：**

1. **Key 绝不下发到前端**（现在就是这么做的）
2. **对话限流**：每用户每天 20 轮，超了提示"明天再来"
3. **答案缓存**：同一篇文章 + 同一个问题，24 小时内直接返回缓存
4. **失败降级**：模型超时/报错 → 返回"这个问题稍后再试"，**不影响看文章**

### 4.3 备用方案

单一供应商有风险（涨价、限流、宕机）。方案：

```js
主：DeepSeek（便宜、中文好）
备：阿里通义 / 智谱 GLM（配置一行切换）
```

接口都是 OpenAI 兼容格式，切换成本几乎为零——代码里已经用 `LLM_BASE_URL` 抽象了。

### 4.4 对话成本是最大变量

文章生成和打分是**固定成本**（每天约 0.15 元），对话是**变动成本**（随用户数线性增长）。

所以：
- 免费用户：每天 5 轮
- 付费用户：每天 50 轮

## 五、成本总账

### 5.1 固定成本（每月）

| 项 | 费用 |
|---|---|
| 香港轻量服务器 2C2G | 40 元 |
| 域名（70/年） | 6 元 |
| SSL 证书 | 0（Let's Encrypt） |
| 代码托管/CI | 0（GitHub 免费） |
| **小计** | **约 46 元/月** |

### 5.2 变动成本

**LLM（按 2 元/百万输入、8 元/百万输出估算）：**

| 规模 | 每日生成 | 每日对话 | LLM 月成本 |
|---|---|---|---|
| 0–100 用户 | 0.10 元 | 1.4 元 | **约 45 元** |
| 1000 用户 | 0.15 元 | 14 元 | **约 425 元** |
| 10000 用户 | 0.2 元 | 140 元 | **约 4200 元** |

**邮件（Resend）：**

| 规模 | 每天发送 | 月成本 |
|---|---|---|
| < 100 订阅 | 100 封 | 0（免费额度 3000/月） |
| 1000 订阅 | 1000 封 | 约 150 元（$20 套餐） |
| 10000 订阅 | 10000 封 | 约 750 元 |

### 5.3 总账

| 规模 | 月成本 | 需要多少收入回本 |
|---|---|---|
| **启动期（<100 用户）** | **约 90 元** | 10 个 C 端订阅（9.9）或 0.5 个 B 端客户 |
| **1000 用户** | **约 620 元** | 62 个订阅，或 **1 个 B 端客户** |
| **10000 用户** | 约 5000 元 | 500 个订阅，或 5 个 B 端客户 |

**结论：B 端一个客户 ≈ 覆盖 1000 用户规模的全年成本。**

### 5.4 一次性成本

| 项 | 费用 |
|---|---|
| 域名首年 | 70 元 |
| 备案（如需） | 0 元，但 2–4 周时间 |
| 支付资质（如需） | 个体户注册 0–500 元 |
| **合计** | **< 600 元** |

## 六、具体技术架构

### 6.1 架构图

```
                  ┌──────────────┐
   用户浏览器 ────▶│   Nginx      │ HTTPS + 静态缓存
                  │  (443/80)    │
                  └──────┬───────┘
                         │
                  ┌──────▼───────┐
                  │  Next.js     │ Docker 容器
                  │  (3000)      │
                  └──┬───────┬───┘
                     │       │
        ┌────────────▼──┐  ┌─▼──────────────┐
        │ SQLite/Postgres│  │ DeepSeek API   │
        │  内容 + 用户    │  │ 摘要/打分/对话  │
        └────────────────┘  └────────────────┘
                     │
        ┌────────────▼─────────────┐
        │ 定时任务（宿主机 cron）    │
        │ 6:30 抓取→打分→生成→部署  │
        └──────────────────────────┘
                     │
              ┌──────▼──────┐
              │ Resend 邮件  │ 每天 7:30 推送
              └─────────────┘
```

### 6.2 数据库表

```sql
sources      (id, name, url, type, category, enabled, brief_only)
candidates   (id, source_id, title, url, published_at, score, reason, status)
articles     (id, url, title, account, summary, questions_json, word_count, published_at, edition)
profiles     (id, name, keywords, min_score, size)          -- default / ai-daily
editions     (id, profile_id, date, article_ids_json)       -- 每天一版
users        (id, email, created_at, plan, plan_expires_at)
chat_logs    (id, user_id, article_id, question, answer, tokens, created_at)
subscribers  (id, email, profile_id, confirmed, created_at)
```

### 6.3 定时任务（宿主机，不放在容器里）

```bash
# crontab -e
30 6 * * * /opt/deepread/scripts/daily.sh >> /var/log/deepread.log 2>&1
30 7 * * * /opt/deepread/scripts/send-mail.sh >> /var/log/deepread.log 2>&1
```

**为什么放宿主机**：容器会重启、会休眠，宿主机 cron 不会。

```
→ 不依赖微信开放平台，个人也能做
```

## 九、一句话总结

> **部署：香港轻量服务器 + 域名，一周上线。**

## 十、获客与分发（修订版）

> 原方案把「邮件」当 C 端主要渠道，是错的。中国用户不读邮件。此处修订。

### 10.1 各渠道的真实位置

| 渠道 | 获客能力 | 留存能力 | 结论 |
|---|---|---|---|
| **微信公众号** | **强**（看一看、搜一搜、朋友圈转发） | 强（关注即订阅） | ✅ **C 端主阵地** |
| 网站 | 弱（没有自然流量） | 中 | 落地页 + 分享名片 + 搜索长尾 |
| 邮件 | **极弱**（中国用户不看邮箱） | 中 | ❌ C 端降级；✅ 保留给 B 端 |
| 小红书 / 知乎 / 即刻 | 中（能引流，但平台限流） | 弱 | 辅助，做内容切片 |
| 微信群 / 朋友圈 | 强（熟人传播） | 中 | 冷启动第一批用户 |
| 小程序 | 中 | 强 | 第二阶段，微信内闭环 |

**结论：**

```
C 端：公众号为主，网站为辅，邮件只做「可选提醒」
B 端：邮件 + 合同，公众号不参与
```

### 10.2 C 端获客漏斗

```
公众号推文（每天 1 篇）
   │  内容是产品本身：8 篇摘要 + 3 个问题
   ▼
读者觉得有用 → 关注 / 转发
   │
   ▼
点「阅读原文」→ 网站
   │  网站上有完整版 + AI 对话
   ▼
收藏 / 加入书签 / 留邮箱
   │
   ▼
（后期）付费订阅
```

**关键认知：公众号的文章本身就是获客素材。** 你不需要"推广"，你需要每天发一篇别人愿意转发的文章。

### 10.3 公众号的现实约束

| 约束 | 影响 | 解法 |
|---|---|---|
| 个人订阅号**每天只能群发 1 次** | 一天只能发一篇 | 刚好：一天一篇「今日精选」 |
| 个人订阅号**没有发布 API** | 不能全自动发 | 每天手动复制粘贴（5 分钟） |
| 认证需要企业主体或 300 元/年 | 高级接口用不了 | 前期不认证，够用 |
| 微信对站外导流敏感 | 链接可能被限 | 只用「阅读原文」位，不在正文放链接 |
| 打开率逐年下降 | 涨粉慢 | 靠「问题」设计提升互动和转发 |

**个人订阅号 vs 服务号：**

- 订阅号：每天 1 次群发，适合日更内容 ✅
- 服务号：每月 4 次群发，适合通知和支付 ❌ 不适合日更

**所以：C 端用订阅号，日更。**

### 10.4 前 100 个订阅者怎么来（冷启动）

不靠算法，靠手工：

1. **朋友圈 + 微信群**：发 3 天，看有没有人主动问"怎么订阅"
2. **垂直社群**：AI 群、产品经理群、投资人群，每天转发当天精选
3. **知乎/小红书**：把当天最好的一篇改写成短文，结尾引导
4. **互推**：找 3–5 个同类小号（1000–5000 粉）互相推荐
5. **朋友圈截图**：把"AI 对话"的截图发出去（这是别人没有的功能）

**前 100 个订阅者，预计 2–4 周，不需要花钱。**

### 10.5 公众号内容怎么生产（每天 5 分钟）

系统已经生成好：8 篇标题 + 摘要 + 3 个问题。

```
① 复制今天的 edition（脚本导出 Markdown/HTML）
② 粘贴到公众号编辑器
③ 配一张头图（可以用每日随机配图）
④ 点群发
```

**可以做到 5 分钟。** 后续如果认证了服务号，可以用 API 自动发草稿箱，连粘贴都省了。

### 10.6 B 端的获客（完全不同）

B 端不靠内容，靠**直接销售**：

```
① 列 50 家目标公司（你熟悉的行业）
② 做一份《AI 行业日报》样刊（3 天的内容）
③ 邮件/LinkedIn/朋友介绍，发样刊
④ 约 15 分钟电话，问三个问题：
   - 你们现在怎么获取行业信息？
   - 每天花多少时间？
   - 如果有人每天 7:30 给你一份摘要，值多少钱？
⑤ 前 3 个客户打 5 折，换案例和反馈
```

**B 端不需要公众号，也不需要流量。**

### 10.7 修订后的成本

| 项 | 原方案 | 修订后 |
|---|---|---|
| 邮件服务 | 150 元/月（1000 订阅） | **降到 ~0**（C 端不用邮件） |
| 公众号 | — | 0 |
| 服务器 | 40 元/月 | 40 元/月 |
| LLM | 425 元/月 | 425 元/月 |

**1000 用户时，月成本从 620 元降到约 470 元。**

### 10.8 修订后的阶段目标

| 阶段 | 渠道 | 目标 |
|---|---|---|
| 1–2 周 | 网站 + 自动更新 | 能发链接 |
| 3–4 周 | **公众号开号 + 日更** | 100 个关注 |
| 5–8 周 | 公众号 + 社群 + 互推 | 500 个关注 |
| 5–8 周（并行） | B 端样刊 + 销售 | 1 个付费客户 |

**公众号不是"以后再说"，是第 3 周就要开的。**

## 十一、公众号每天写什么

### 11.1 先纠正一个误解

**技术上完全可以把网站内容搬到公众号**——复制粘贴就行，没有任何限制。

**但不该全搬。** 原因有三：

1. **版权**：全文转载别人的文章有风险；只引用标题 + 100 字摘要 + 链接是安全的
2. **产品逻辑**：公众号看全了，谁还去网站？网站才是能对话、能订阅的地方
3. **推荐权重**：微信的「看一看」偏爱原创内容，纯摘要合集会被判定低质

**所以公众号的定位是：预告片，不是正片。**

### 11.2 公众号内容结构（每天固定模板）

```
标题：今天值得读的 8 篇（11 月 12 日）

【开头 150 字】编辑按语
  今天为什么选这些？这批文章有什么共同点？
  —— 这部分必须是原创，也是原创声明的依据

【主推 1 篇】约 500 字
  - 为什么值得读（不是复述内容，是说"它解决了什么疑问"）
  - 3 个问题
  - 一句"完整版和 AI 对话在原文链接里"

【其余 7 篇】每篇 2 行
  - 标题
  - 一句话推荐 + 1 个问题

【结尾】
  阅读原文 → 网站看完整版、和 AI 聊这篇
```

**全文约 1200–1500 字，10 分钟能写完，5 分钟能排版。**

### 11.3 为什么这个结构能涨粉

| 设计 | 作用 |
|---|---|
| **主推 1 篇而不是 8 篇** | 读者有明确入口，不会滑走 |
| **编辑按语** | 提供"人"的观点，这是 AI 产品最缺的东西 |
| **3 个问题** | 引发评论区讨论 → 提升推荐权重 |
| **其余 7 篇只给一句话** | 制造信息缺口，逼读者点"阅读原文" |
| **结尾引导到网站** | 公众号涨粉，网站做转化 |

### 11.4 内容来源与工作量

系统每天生成：8 篇标题 + 摘要 + 问题。
**你要额外写的只有：150 字按语 + 1 篇 500 字导语。**

如果连这个都不想写，可以让 DeepSeek 生成初稿，你改两句——但要保留"人味"，纯 AI 文案在微信里很难涨粉。

### 11.5 三条红线

1. **不放全文**：只放标题 + 100 字内摘要，正文链接到原文
2. **正文不放站外链接**：只在「阅读原文」位放（微信对正文外链敏感）
3. **不要日更超过 1 篇**：订阅号一天只能发一次，攒着一起发效果更好

## 十二、登录与埋点

### 12.1 第一版：不用登录

| 功能 | 要不要登录 |
|---|---|
| 读每天的 8 篇 + 速览 | ❌ 不要 |
| 点问题和 AI 对话 | ❌ 不要（匿名，按浏览器标识限流） |
| 邮件订阅 | ✅ 只要邮箱，不要密码 |
| 付费 | ✅ 需要账号 + 订单 |

**结论：V1 全站匿名可读，只在「订阅」和「付费」两个动作上要身份。**

这和现在一致，不用改。

### 12.2 埋点怎么做（无登录也能统计）

**核心思路：匿名访客 ID + 事件表。**

```js
// 首次访问生成，存 localStorage，永不上传个人信息
const aid = localStorage.getItem('dr_aid') || crypto.randomUUID();
localStorage.setItem('dr_aid', aid);
```

前端上报（用 sendBeacon，不阻塞页面）：

```js
navigator.sendBeacon('/api/track', JSON.stringify({
  aid, name: 'article_click', props: { id, position: 3 }, path: location.pathname
}));
```

后端一张表：

```sql
CREATE TABLE events (
  id INTEGER PRIMARY KEY,
  aid TEXT,              -- 匿名标识
  name TEXT,             -- page_view / article_click / question_click / chat_sent
  props TEXT,            -- JSON
  path TEXT,
  referrer TEXT,
  created_at TEXT
);
```

### 12.3 第一版只埋 4 个事件

| 事件 | 什么时候发 | 能回答什么问题 |
|---|---|---|
| `page_view` | 打开首页 | 今天有多少人来看 |
| `article_click` | 点标题去原文 | 内容有没有吸引力（人均读几篇） |
| `question_click` | 点某个问题 | **核心功能的吸引力** |
| `chat_sent` | 发出对话 | 从"好奇"到"真用"的转化 |

订阅和付费单独记（`subscribe`、`paid`），因为涉及身份。

### 12.4 第一版要不要做？

**要做，但只做半天的工作量。**

理由：

- 没有数据，你判断不了"内容好不好"——只能凭感觉
- B 端客户会问"有多少人在用"，你要答得出来
- 有了 4 个事件，就能算出三个关键指标

**不要做的：**

- ❌ Google Analytics / 百度统计：国内不稳、数据出境合规风险、自定义事件难用
- ❌ 完整的漏斗看板：第一版用不上
- ❌ 用户画像/路径分析：样本太小，没有统计意义

### 12.5 每周只看三个数

```
① 次日留存：今天来的人，明天还来吗？（目标 > 20%）
② 人均阅读：一次打开读几篇？（目标 > 2.5 篇）
③ 对话转化：多少比例的人点了问题？（目标 > 15%）
```

一个脚本每周跑一次，输出一张表，够用了。

### 12.6 隐私合规

- 采集匿名 ID，**不采集手机号、微信、IP 完整地址**
- 隐私政策里写一句："我们使用匿名标识统计使用情况，不收集个人身份信息"
- 埋点数据只用于产品改进，不对外提供

## 十三、开发顺序（施工图）

### 13.1 排期的三条原则

1. **存储改造必须最先做** —— 埋点、订阅、登录全都要写数据库，它是一切的地基
2. **先能跑，再能看，再能收钱** —— 顺序不能反，否则会做一堆用不上的功能
3. **每个阶段都有"可验收的产物"** —— 做完就能给别人看，避免半成品堆积

### 13.2 五个阶段

```
阶段 1  能上线（W1–W2）      服务器 + 存储 + 定时   → 3 天不碰电脑也有更新
阶段 2  能看数据（W3）       埋点 + 周报 + 公众号导出 → 知道谁在看
阶段 3  能订阅（W4）         邮箱订阅 + B 端落地页    → 有第一批订阅者
阶段 4  能收钱（W5–W6）      登录 + 付费 + 额度      → 能卖
阶段 5  多版本（W7）         多 profile + 客户定制   → 能卖第二个行业
```

### 13.3 任务清单

#### 阶段 1：能上线（5 个工作日）

|---|---|---|---|---|

| 1.2 | Docker + compose + Nginx + HTTPS 证书 | 0.5 天 | 1.1 | 我 |
| 1.3 | **JSON → SQLite 迁移**（表结构 + 迁移脚本） | 1.5 天 | — | 我 |
| 1.4 | 定时任务 `daily.sh`（召回→打分→生成→发布） | 0.5 天 | 1.3 | 我 |

**验收：连续 3 天不碰电脑，每天早上打开就有 8 篇 + 5 条速览。**

### 13.5 一条不能违反的规则

> **每个阶段结束前，不做下一个阶段的事。**

阶段 1 没跑满 3 天自动更新，就不要开始埋点；阶段 2 没有 100 个读者，就不要做付费。

原因很现实：**你是一个人**。同时开三条战线，最后一条都完不成。

### 13.6 什么可以先不做

| 在线支付 | 前 10 个客户手动收款更快 |
| 评论/点赞 | 没有用户量时是负资产 |
| 搜索 | 每天 8 篇，翻两屏就到底了 |

## 十四、如果一定要做 App：开发、审批、难点

### 14.1 三条技术路线

| 路线 | 工时 | 体验 | 风险 |
|---|---|---|---|
| **A. WebView 套壳** | 3–5 天 | 差（像网页） | **苹果 4.2 大概率拒** |
| **B. React Native / Flutter** | 4–6 周（单端） | 好 | 双端再 +2–3 周 |
| **C. 原生双端** | 8–12 周 | 最好 | 一个人维护不动 |

**如果真要做，选 B。** A 省时间但过不了审，C 你维护不起。

### 14.2 开发清单（B 路线，MVP）

**客户端**

| 模块 | 工时 |
|---|---|
| 登录（手机号/微信） | 3 天 |
| 首页（每日 edition） | 3 天 |
| 文章详情（含原文链接） | 2 天 |
| AI 对话（流式输出） | 4 天 |
| 订阅支付（iOS 内购 / 微信支付） | 5 天 |
| 推送（每日更新提醒） | 2 天 |
| 分享、收藏、离线缓存 | 3 天 |
| **小计** | **约 22 天** |

**服务端改造**

| 模块 | 工时 |
|---|---|
| REST API 版本化 + Token 鉴权 | 3 天 |
| 推送服务（APNs / 厂商推送） | 2 天 |
| 支付回调 + 订单校验（双渠道） | 4 天 |
| 内容审核（AI 对话要过滤 + 举报） | 3 天 |
| **小计** | **约 12 天** |

**总计：约 7 周（一个人全职）**，还没算测试和上架折腾。

### 14.3 审批：这是真正的门槛

#### iOS（苹果）

| 项 | 要求 | 周期 |
|---|---|---|
| Apple Developer | **688 元/年** | 1–3 天 |
| **ICP 备案** | 中国区上架必须 | 2–4 周 |
| **App 备案**（工信部） | 2023 年起强制 | 2–4 周 |
| App Store 审核 | 每轮 1–3 天 | 常见 2–4 轮 |

**常见拒因（按概率）：**

| 条款 | 问题 | 我们的处境 |
|---|---|---|
| **3.1.1 内购** | 数字订阅必须走 IAP，苹果抽 **15–30%** | **最大成本**：9.9 元订阅到手 6.93 元 |
| **4.2 最低功能** | 套壳网页直接拒 | 走 B 路线可避开 |
| **1.2 用户内容** | AI 对话属于 UGC，要有过滤 + 举报 | 必须做 |
| **5.1.1 隐私** | 隐私政策 + 数据清单 | 一般能过 |

#### Android（国内商店）

| 项 | 要求 | 周期 |
|---|---|---|
| **软件著作权** | 华为/小米/OPPO 普遍要求 | 1–2 个月（加急 3–5 天，几百元） |
| **App 备案** | 同上，强制 | 2–4 周 |
| **ICP 备案** | 强制 | 2–4 周 |
| 隐私合规（164 号文） | 权限说明、不得超范围收集 | 会被抽查通报 |
| 各商店审核 | 华为/小米/OPPO/vivo/应用宝 分别提交 | 每家 3–7 天 |

**个人开发者上架受限**：华为、小米等对个人开发者收紧，部分类目只对企业开放。

### 14.4 最致命的一条：新闻资质

这是绕不过去的：

> 《互联网新闻信息服务管理规定》要求，提供**互联网新闻信息采编发布、转载服务**，必须取得**《互联网新闻信息服务许可证》**。

拿证条件（摘要）：

- 必须是**法人**（个人不行）
- 有新闻编辑人员、场所、资金
- 有健全的管理制度

**我们的产品形态——「精选别人的文章 + 摘要 + 链接」——在监管口径里可能被认定为「转载服务」。**

网站层面相对宽松（备案即可），但 **App 和小程序上架时，应用商店会要求你选「新闻资讯」类目并提交资质**。没有资质，要么选错类目被拒，要么上架后被下架。

**小程序同理：**

- 个人主体小程序**不能选新闻资讯类目**
- 个人主体**不能开通微信支付**（要企业/个体户）

### 14.5 成本汇总（App 版）

| 项 | 金额 |
|---|---|
| 苹果开发者 | 688 元/年 |
| 软著（加急） | 500–1500 元 |
| 域名 + 服务器 | 约 550 元/年 |
| **苹果抽成** | **订阅收入的 15–30%** |
| 开发时间 | **7 周** |
| 备案时间 | **2–4 周**（并行） |

### 14.6 结论：现在不做

| 维度 | 判断 |
|---|---|
| 技术 | 能做，7 周 |
| 审批 | **难过**（新闻资质 + 备案 + 双端商店） |
| 经济 | **不划算**（30% 抽成 + 7 周开发，换来的日活可能不如公众号） |
| 合规 | **个人主体基本走不通** |

**替代方案（体验接近，门槛低得多）：**

```
① PWA：网页"添加到主屏幕"，有图标、全屏、推送（Android 支持）
② 小程序：微信内闭环，但个人主体受限（不能支付、不能选资讯类目）
③ 公众号：最轻，零审核，直接触达
```

**建议顺序不变：公众号 → 网站 → （有公司主体再考虑）小程序 → App。**

### 14.7 什么情况下才值得做 App

三个条件**同时满足**时再考虑：

1. 已经注册了公司（能办资质、能开发票）
2. 月活 > 5000（撑得起下载和留存）
3. 有至少一款付费产品在跑（能承担 30% 抽成）

否则，投入 7 周做一个日活几百的 App，是最典型的副业陷阱。
