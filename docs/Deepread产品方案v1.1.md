# Deepread 产品方案 v1.1

> 2026-11-01 · **规划稿，暂不开工**
> 前置条件：v1.0 跑满 14 天并达到验收指标（见第 9 节）
> 上一版：[Deepread 产品方案 v1.0](Deepread产品方案v1.0.md)

---

## 0. 这一版解决什么

v1.0 是「人工贴 5 条 → AI 加工」。它验证的是**问题机制**成不成立。

v1.1 解决两个规模问题：

1. **不用每天手工找文章**——建立召回链路，自动产出候选池
2. **不再只有科技**——接入播客和更多垂直源，覆盖历史 / 文艺 / 经济

**但 v1.1 不改产品核心**：仍然是每天 5 篇、仍然每篇一个问题、仍然不登录。变的只是"文章从哪来"和"多了一个每周长内容"。

---

## 1. 从 v1.0 到 v1.1

| | v1.0 | v1.1 |
|---|---|---|
| 内容来源 | 人工贴 5 条 | **自动召回 + 人工补 3 条** |
| 候选池 | 5 条 | **每天 100–300 条** |
| 排序 | 无（人选） | **粗排 → Jev 精排 → 重排** |
| 类目覆盖 | 你贴什么有什么 | **科技自动、其余靠播客 + 人工** |
| 内容形态 | 只有文章 | **文章 + 每周一期长内容（播客）** |
| 列表结构 | 一层 | **两层：主列表 5 篇 + 链接池 20 条** |
| 人的角色 | 找文章 + 审问题 | **只审问题，偶尔补链接** |

---

## 2. 产品形态：两层列表

这是 v1.1 最重要的结构变化。

```
┌─ 主列表（5 篇）──────────────────────────────┐
│ 必须有正文 → 有摘要、有问题、有 AI 答案        │
│ 这是差异化所在，100% 有提问                    │
└──────────────────────────────────────────────┘

┌─ 链接池（20 条）─────────────────────────────┐
│ 只有标题 + 来源 + 链接                        │
│ 抓不到正文的、分数不够的、时效稍旧的都放这里    │
│ 一行一条，不做任何加工                         │
└──────────────────────────────────────────────┘
```

**为什么分两层**：

- 如果混在一起，用户点开发现一半没有摘要——产品退化成热摸爽
- 分开之后，主列表的品质是稳定的，链接池提供广度
- 抓不到正文的内容（公众号风控、知乎反爬）也有位置，不会浪费

## 3. 召回链路

### 3.1 四类源

| 类型 | 协议 | 中文覆盖 | 正文获取 | 维护成本 |
|---|---|---|---|---|
| **RSS** | 标准 | 中（科技强） | HTML 提取 | 低 |
| **播客** | 标准 RSS | 好（历史/文艺/商业） | ASR 转录 | 中 |
| **Newsletter** | Substack `/feed` | 窄 | HTML / 邮件正文 | 低 |
| **公众号** | 无公开协议 | **最重要** | 单篇可抓，批量不行 | **极高** |

**注意最后一行**：中文最重要的内容在公众号，而它是唯一没有协议的。这一行决定了 v1.1 仍然是"自动 + 人工"的混合模式。

### 3.2 源清单与优先级

**P0（v1.1 第一批）**

| 源 | 类型 | 覆盖 |
|---|---|---|
| InfoQ 中文、量子位、少数派、钛媒体、开源中国 | RSS | 科技 |
| 经济观察报 | RSS | 经济 |
| 忽左忽右、跳岛 FM、商业就是这样 | 播客 | 历史 / 文艺 / 经济 |
| 人工投喂（你每天 3 条） | 手动 | 全部 |

**P1（第二批）**

| 源 | 类型 | 覆盖 |
|---|---|---|
| Substack 中文作者（逐个确认） | RSS | 商业 / 科技 |
| 反派影评、文化有限 | 播客 | 影视 / 文学 |

**P2（观察）**

- 公众号第三方中转（wechat2rss）——稳定性差、有封号风险，**不主动做**
- 榜单类（GitHub Trending、知乎热榜）——只作为"话题线索"，不直接当内容源

### 3.3 公众号怎么办

三条路，按推荐度排：

1. **人工投喂（推荐）**——你每天贴 3 条，系统抓正文做加工
2. **作者授权**——以后做大了再谈
3. **第三方中转**——不做，风险和收益不成比例

## 4. 排序链路

```
召回（100–300 条/天）
   ↓ 粗排（规则，零成本）
30–50 条
   ↓ 精排（Jev，便宜）
10–15 条
   ↓ 重排（配额 + 去重）
主列表 5 篇 + 链接池 20 条
```

### 4.1 粗排（规则，不调模型）

| 步骤 | 规则 |
|---|---|
| 去重 | URL 规范化 → 标题 SimHash → 语义相似度 0.92 |
| 时效 | 超过 7 天的不进主列表（可进链接池） |
| 黑名单 | 标题关键词 + 源黑名单 |
| 源权重 | 低权重源排在后面 |

**这一步要挡掉 80%**，因为精排按 token 收费。

### 4.2 精排（Jev）

沿用 v1.0 的三问设计，但**不喂正文**（成本考虑），只喂：

```
state: { title, account, summary（RSS 摘要或 og:description） }
questions: { worth(0-5), category, kind }
```

**这里有个权衡**：不喂正文，准确率会降。所以分两个阶段：

```
第一轮：全部候选，只用标题 + 摘要打分（便宜）
第二轮：分数 ≥3 的在抓正文后再打一次分（贵但准）
```

两轮都过，才进主列表候选。

### 4.3 重排（规则）

| 规则 | 说明 |
|---|---|
| **同事件去重** | 同一件事只留一篇（向量相似度 > 0.85 视为同事件） |
| **类目配额** | 科技 2 / 历史 1 / 经济 1 / 文艺 1（可调） |
| **来源多样性** | 同一账号最多 1 篇 |
| **新鲜度** | 24 小时内的优先 |

配额不是死的：某类目当天没有好文章，就把名额让给其他类目。

### 4.4 核心指标：好文章密度

```
好文章密度 = 精排 ≥3 分的条数 / 召回总条数
```

| 密度 | 含义 | 该怎么办 |
|---|---|---|
| ≥ 10% | 源选对了 | 继续扩源 |
| 3–10% | 能用，但要多召回 | 扩源 + 调权重 |
| < 3% | 源不对 | **先换源，别调排序** |

**这个指标决定 v1.1 成不成立。** 如果密度一直低于 3%，说明能自动抓到的源里根本没有你要的内容——那就得回到"人工为主"。

## 5. 每周长内容（播客）

### 5.1 为什么单开一档

一期播客 60 分钟，信息量相当于一万字长文。塞进每日 5 篇会撑爆用户的注意力，拆成 5 条更怪。

所以：**每日 5 篇是文章，每周 1 期是长内容。**

### 5.2 转录方案

```
播客 RSS（含 audio url）
   ↓ 下载音频
whisper.cpp 本地转录（M 系列约 10 倍实时，60 分钟音频约 6 分钟）
   ↓ 得到带时间戳的文本
分段（按 5–8 分钟切）
   ↓
Jev 选"最值得听的 3 段" + LLM 从这 3 段里生成 3 个问题
```

**为什么本地转录**：云 ASR 一期 60 分钟约 5–8 元，一周一期就是 20–30 元/月；本地 0 元，只是占 6 分钟 CPU。

### 5.3 卡片形态

```
┌──────────────────────────────────────────┐
│ 播客 · 忽左忽右                           │
│ 第 312 期：安史之乱前的那个冬天            │
│ 嘉宾：XXX（唐史研究者） · 68 分钟          │
│                                          │
│ 摘要：……                                 │
│                                          │
│ ❓ 为什么安禄山起兵时，长安城里几乎没人     │
│    相信他真的会反？                       │
│                                          │
│ 00:23:40 听这段 →                         │
└──────────────────────────────────────────┘
```

**时间戳是核心设计**：不想听完整期的人，可以直接跳到关键段落。这比文章的"读原文"更精准。

### 5.4 版权边界

| 能做 | 不能做 |
|---|---|
| 摘要（150 字内） | 发布完整转录稿 |
| 引用 3–5 句原话（≤100 字） | 剪辑音频重新发布 |
| 链回原节目 | 去掉节目信息二次分发 |

## 6. 分类

沿用 v1.0 的三级兜底，但加一条播客特有的：

```
① 账号 / 节目映射表（人工维护，命中率最高）
   "忽左忽右"    → 历史
   "跳岛 FM"     → 文艺
   "商业就是这样" → 经济
        ↓ 未命中
② Jev 判断（标题 + 账号 + 摘要）
        ↓ 置信度低
③ 归入「其他」，后台一键改
```

**播客的映射特别准**，因为一档节目通常只做一个领域。

## 7. 数据模型（相对 v1.0 的新增）

```sql
-- 源
create table sources (
  id           text primary key,
  name         text not null,
  type         text not null,      -- rss / podcast / newsletter / manual
  url          text not null,
  category     text,
  weight       smallint default 50,
  enabled      boolean default true,
  last_ok_at   timestamptz,
  fail_count   int default 0
);

-- 候选池（召回但还没发布的）
create table candidates (
  id           bigserial primary key,
  source_id    text references sources(id),
  kind         text not null,      -- article / podcast
  url          text unique not null,
  title        text not null,
  summary      text,
  published_at timestamptz,
  fetched_at   timestamptz default now(),

  dedupe_key   text,
  rough_score  real,               -- 粗排分
  worth        real,               -- Jev 精排分
  worth_conf   real,
  category     text,
  kind_label   text,               -- 深度/快讯/通稿/评测
  judged_at    timestamptz,

  status       text default 'new'  -- new / shortlisted / published / dropped
);

-- 发布层（原来 articles 表加两个字段）
alter table articles add column source_type text;   -- rss / manual / podcast
alter table articles add column layer text;         -- main / linkpool

-- 播客
create table podcasts (
  id            bigserial primary key,
  show          text not null,
  episode_title text not null,
  audio_url     text,
  duration_s    int,
  transcript    text,             -- 转录全文（仅内部用，不对外）
  segments      jsonb,            -- [{start, end, text}]
  published_at  timestamptz
);
```

**注意 `podcasts.transcript` 存了全文**——这是唯一存正文的地方，因为转录要花 6 分钟，每次都重跑不现实。**但它永远不对外展示，只用于生成摘要和问题。**

## 9. 开工前置条件

**v1.1 不开工，除非 v1.0 同时满足：**

| # | 条件 | 判定 |
|---|---|---|
| 1 | 连续 14 天每天发 5 篇 | 做不到说明产能或流程有问题 |
| 2 | 你自己每天点开 ≥ 3 篇 | 做不到说明选题不行 |
| 3 | 至少 5 个朋友说"这个问题问得好" | 做不到说明差异化不成立 |
| 4 | 攒够 50 组「文章 + 问题」的人工修改记录 | 这是校准 prompt 的原料 |

**第 3 条最重要。** 如果没人觉得问题好，那 v1.1 做得再自动，也只是更快地生产平庸内容。

## 10. 排期（满足前置条件后）

| 阶段 | 时间 | 交付 |
|---|---|---|
| **A 召回** | 2 周 | 3 类源（RSS + 播客 + 人工）跑通，候选池每天 100+ |
| **B 排序** | 1 周 | 粗排 + 两轮精排 + 重排，每天自动出 5 篇 + 20 条链接池 |
| **C 播客** | 2 周 | 转录 + 分段 + 3 个问题 + 时间戳卡片 |
| **D 打磨** | 1 周 | 后台审核、手动改分类、指标看板 |

**共 6 周。** 比 v1.0 长，因为召回是持续维护的活。

## 11. 风险

| 风险 | 概率 | 影响 | 对策 |
|---|---|---|---|
| **好文章密度低于 3%** | 中 | **致命** | 回到人工为主，自动只做辅助 |
| 播客转录质量差 | 中 | 中 | 只选口齿清晰、有 show notes 的节目 |
| 自动召回后问题变平庸 | **高** | **致命** | 问题仍逐条人工过，不自动化 |
| 成本失控 | 低 | 低 | 两轮精排已经控住了 |
| 版权投诉 | 低 | 中 | 只发摘要 + 引用，链回原处 |

---

## 12. 明确不做

| 不做 | 原因 |
|---|---|
| ❌ Twitter / X 接入 | API 贵、中文噪音大、要代理 |
| ❌ YouTube 接入 | 字幕不全、要代理、和"阅读"定位不符 |
| ❌ 公众号批量抓取 | 违反平台规则，必被封 |
| ❌ 全文入库（文章） | 合规底线，只存摘要和摘录 |
| ❌ 问题全自动发布 | 问题必须人工过一遍，这是唯一的护城河 |
| ❌ 登录 / 个性化 | 仍然不需要 |

---

## 13. 一句话总结

**v1.1 把「找文章」这件事自动化，但把「问问题」这件事留给人。**

前者是工程，后者是产品。搞反了，这个产品就没有存在理由了。
