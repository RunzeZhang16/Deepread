## 一、这是什么

**Deepread 是一个每周只出 8 篇的中文阅读产品。**

它每周五晚 7 点自动完成三件事：

1. 从约 300 个中英文媒体和独立博客里，捞出当天新发的文章
2. 给每篇打分，挑出最适合普通人读的 8 篇
3. 给每篇写一段摘要、一个"钩子"、两个问题——**读者点问题，就能和 AI 聊这篇文章**

核心差异点不是"推荐"，而是**读完还能接着问**。

### 目标读者

- 想读点好东西，但没时间在信息流里筛
- 不是技术从业者，不需要行业深度分析
- 每天愿意花 20–40 分钟认真读几篇长文

### 产品边界（三条底线）

| 底线 | 做法 |
|---|---|
| **不存正文** | 只存标题、摘要、问题、≤300 字摘录、原文链接 |
| **不做时政军事** | 选题偏科技、经济、科学、人文、社会 |
| **不搞付费墙** | 摘要和问题永久免费 |

## 二、用户能用到什么

### 2.1 页面地图

| 页面 | 地址 | 作用 |
|---|---|---|
| **本期** | `/` | 8 篇正文 + 订阅入口 |
| **往期** | `/archive` | 历史每一期 |
| **某一期** | `/archive/2026-11-15` | 那一天的 8 篇 + 速览 |
| **收藏** | `/saved` | 本地收藏，14 天自动清理 |
| **公众号排版** | `/wechat` | 一键生成公众号文案 |
| **召回池** | `/recall` | 运营后台：看候选、换源、手动加文章 |

### 2.2 每篇文章长什么样

```
◇ 成绩没有下降 孩子却快撑不住了 警惕中小学生藏在优秀背后的情绪危机   ☆
  摘要：100–120 字，讲清文章说了什么、最有价值的那一点
  01  成绩没下降，孩子心理怎么还会出问题？
  02  这些孩子身上通常有什么共同点？
  经济观察报 · 2232 字
```

- **◇ 菱形**：颜色代表分类（科技蓝 / 社会绿 / 人文紫 / 科学金 / 经济砖红）
- **标题下划线**：颜色随分类变
- **☆**：收藏（存浏览器本地，7 天过期）
- **点击问题**：展开对话面板，直接给出预生成的答案

### 2.3 对话的规则

```
每篇文章 3 轮
  ├─ 第 1、2 轮：点展示的问题 → 读预生成答案（不调用模型，秒回）
  └─ 第 3 轮：自己打字或点 AI 的追问 → 真正调用模型
用完后提示：「感谢您的好奇心，但是这篇文章的对话额度已经用完啦…」
```

**为什么展示问题的答案要预生成**：如果每个用户点一次问题都调一次模型，每天几百次点击就是几块钱；预生成后，这部分成本是 0，只有真正追问才花钱。

### 2.4 订阅

```
首页 8 篇下方 → 输入邮箱 → 收到确认信 → 点确认 → 每周五晚 7 点收到邮件
```

邮件内容是：**期号 + 网站链接 + 8 篇标题**，不含主题标题、主题总结和摘要（这些需要人工校对后才能发公众号）。

## 三、每周五 19:00 发生了什么

服务器上一条 cron 触发整条流水线，全程约 3–5 分钟：

```bash
0 19 * * 5 /opt/deepread/deploy/run-daily.sh
```

```
周五 19:00  ① 召回 recall
             约 300 个源 → 抓标题和链接 → 写进 candidates（约 1000 条/期）
                   ↓
           ② 打分 rank
             新条目每 12 条一批交给模型，打 0–100 分 + 一句理由
                   ↓
           ③ 出刊 edition
             从过去 7 天的候选里按「衰减后的分数」排序 → 同源最多 2 篇 → 取 8 篇
             → 抓正文 → 生成摘要 + 钩子 + 2 个问题 + 每个问题的答案
             → 生成本期主题（标题 + 每篇贴合度排序）
             → 写入 articles，edition = 周五当天
                   ↓
19:03      ④ 发信 daily-mail
             给所有已确认订阅者发「Deepread 第 N 期」：链接 + 8 个标题
                   ↓
           ⑤ 发公众号稿 wechat-mail
             带题记、按语、8 个标题（无摘要）的排版稿 → 发到自己邮箱
```

**每一步失败都不会中断后面的步骤**（`run()` 包装，失败只记日志）。

### 选稿的三条规则

| 规则 | 数值 | 为什么 |
|---|---|---|
| 时间窗口 | 过去 7 天 | 周五只选当天会凑不满 8 篇 |
| 新鲜度衰减 | 每旧一天 −5%，最多 −30% | 否则周一的高分文章会霸榜一整周 |
| 分数下限 | ≥ 60 | 低于 60 宁可少发，也不凑数 |
| 同源上限 | 2 篇 | 防止一家媒体刷屏 |
| 失败补位 | 自动 | 抓不到正文或生成不合格时，从池子里补下一篇 |

**出刊可重复执行**：先清掉当期正文再重建，不会越跑越多。

### 主题与排序（一期只有一份顺序）

```
出刊时：8 篇标题 + 钩子 → 模型找共性 → 主题标题 + 每篇贴合度分数
                          ↓
                  存进 settings（key = theme_<edition>）
                          ↓
        ┌─────────────────┼─────────────────┐
      网页              公众号稿            订阅邮件
   （接口顺序）        （生成时读取）      （发送时读取）
```

**关键约束**：任何展示层都不允许再排序。首页曾经在 `useMemo` 里按分数重排，导致网页与公众号顺序不一致——这条教训写在代码注释里。

### 期号规则

```
2026-11-14、2026-11-15  测试期，不算期号
2026-11-20 起             第 1 期
```

期号 = 从 `ISSUE_START_EDITION`（默认 `2026-11-20`）起算的期数。早于该日期的出刊不会发订阅邮件。

## 四、技术栈

| 层 | 选型 | 为什么 |
|---|---|---|
| 框架 | **Next.js 15.5**（App Router）+ React 19 + TypeScript | 一个进程同时提供页面和 API，适合小项目 |
| 存储 | **SQLite**（better-sqlite3） | 单机单进程，不需要独立数据库服务；WAL 模式 |
| 正文提取 | **@mozilla/readability** + jsdom | Firefox 阅读模式同款，正文识别准 |
| 抓取 | 自研 `lib/listpage.mjs` + `rss-parser` | 双通道：RSS 优先，没有 RSS 就解析列表页 |
| 模型 | **DeepSeek `deepseek-flash`** | 便宜（打分 + 生成每天约 0.2–0.5 元）、中文好 |
| 邮件 | **nodemailer** + 163 SMTP | 零成本起步；超过约 50 个订阅者换专业服务 |
| 部署 | 腾讯云轻量 2C2G（上海）+ Docker | 国内访问 70ms；单容器够用 |
| 样式 | 原生 CSS（无框架） | 页面简单，避免引入 Tailwind 之类的额外复杂度 |

**没有用到的**：没有 Redis、没有消息队列、没有 ORM、没有 CDN、没有微服务——这个体量都用不上。

## 五、系统架构

```
                    ┌─────────────────────────────┐
   每周五 19:00 cron → │  run-daily.sh               │
                    │  recall → rank → briefs     │
                    │  → edition → mail           │
                    └──────────────┬──────────────┘
                                   │ 直接写库（不走 API）
                                   ▼
                    ┌─────────────────────────────┐
                    │  SQLite  /app/data/deepread.db │
                    │  sources / candidates /      │
                    │  articles / subscribers /    │
                    │  events / settings           │
                    └──────────────┬──────────────┘
                                   │ 读
                                   ▼
  读者 ──────────────────▶  Next.js（容器 deepread:3000）
                                   │
                    ┌──────────────┼──────────────┐
                    ▼              ▼              ▼
              首页/往期      对话 API        订阅 API
              /saved                        ↓
                                       DeepSeek API
                                       163 SMTP
```

**关键设计**：公开站点以 `READONLY=1` 运行，所有写操作（加文章、改状态）在线上被禁止，只有**服务器上的定时脚本**直接写数据库。这样即使有人知道接口地址，也改不了数据。

## 六、数据模型

11 张表，全部在 `db/schema.sql`。

### 内容侧

| 表 | 存什么 | 关键字段 |
|---|---|---|
| **sources** | 抓取源（约 300 个） | `url, type(rss/html), category, brief_only, enabled` |
| **candidates** | 候选池（没选上的文章） | `title, url, score, reason, status(new/promoted/discarded)` |
| **articles** | 已出刊的文章 | `title, summary, questions, answers, hook, edition, title_only` |

`articles.answers` 是一个 JSON 数组，存的就是每个展示问题的答案和追问：

```json
[{"q":"成绩没下降，孩子心理怎么还会出问题？","a":"…","next":"这种硬撑会先从哪些地方露出来？"}]
```

### 用户侧

| 表 | 存什么 |
|---|---|
| **subscribers** | 邮件订阅者（`status: pending / confirmed / unsubscribed`） |
| **chat_quota** | 每篇文章的对话额度（`aid + article_id + day`） |
| **events** | 埋点事件（`page_view / article_click / chat_sent / subscribe_submit …`） |
| **chat_usage** | 旧版按人按天的额度（已废弃，保留兼容） |
| **users / orders** | 会员和订单（预留，V1 没用） |
| **job_runs** | 任务执行记录（预留） |
| **settings** | 键值配置：公众号标题/按语缓存、召回统计 |

`edition` 是这套系统的核心概念：**一期 = 一个 `YYYY-MM-DD` 字符串**。首页只显示 `MAX(edition)`，往期按它分组，历史文章标成 `'0000-00-00'` 不外露。

## 八、关键实现原理

### 8.1 内容是怎么抓进来的

每个源走两条通道之一：

```
探测 URL
  ├─ 是 RSS？ → rss-parser 解析
  └─ 不是？   → 抓 HTML → 从 <a> 里找"像文章链接"的（路径含 4 位以上数字、标题 8–70 字）
```

**踩过的坑：**

| 站点 | 问题 | 解法 |
|---|---|---|
| 中国新闻周刊 | GB2312 编码，直接读全是乱码 | 嗅探 charset，用 `TextDecoder('gbk')` |
| 南方周末 | 日期在 HTML 属性里（`data-time`），不是正文 | 从整页正则找 `YYYY-MM-DD` 兜底 |
| 华尔街见闻 / 36氪 | 首页只有 3KB，内容全靠 JS 渲染 | **放弃**（不引入无头浏览器） |
| 三联生活周刊 | robots.txt 明确 `Disallow: /` | **不抓**（尊重 robots） |
| 第一财经 | 标题尾巴带「16513 8小时前 3评论」 | `cleanTitle` 循环剥离 |

### 8.2 打分

```
输入：标题 + 来源 + 摘要（如果有）
输出：{"score": 0-100, "reason": "一句话理由"}
批量：12 条一次
```

**为什么要打分**：候选池每天约 1000 条，人工挑 8 篇不现实。

**prompt 的关键约束**：面向普通读者。技术深度分析（源码解读、算法细节）**最高 55 分**——这类内容再好也不该进这 8 篇。

### 8.3 出刊：怎么保证稳定

```js
// 简化的选稿逻辑
for (每条候选) {
  if (已选够 8 篇) break;
  if (这个源已经选了 2 篇) continue;      // 同源限制
  if (分数 < 60) continue;                // 分数下限
  if (今天已经发过) continue;              // 幂等

  抓正文 → 太短（<400 字）？跳过，从池子补下一篇
  生成摘要/钩子/问题/答案 → 不合格？跳过，从池子补下一篇
  写入 articles（edition = 今天）
}
```

**三个失败点都有兜底**：抓不到正文、生成失败、验证不通过——任一情况都会自动从候选池补位，所以"8 篇"几乎不会缺。

### 8.4 内容生成与校验

一次模型调用同时产出四样东西：

```json
{
  "summary": "100–120 字，讲清文章说了什么",
  "hook": "20–35 字，最反常识的那个点，不给结论",
  "items": [
    { "q": "问题（≤25 字）", "a": "答案（60–150 字）", "next": "追问（≤25 字）" }
  ]
}
```

**校验规则**（不合格就重试，重试失败就换文章）：

| 字段 | 规则 |
|---|---|
| summary | 40–220 字，不能以「本文」「作者」开头 |
| hook | 10–70 字 |
| 问题 | 4–40 字，必须以问号结尾或疑问词开头，最多 2 个 |
| 答案 | 20–400 字 |

**为什么有这么多限制**：模型很爱写"本文讲述了……"这种废话摘要，以及"为什么不如《罗密欧与朱丽叶》出名"这种无意义对比。校验把这类输出直接挡掉。

### 8.5 跨源去重：为什么不用字符串相似度

同一件事，不同媒体写法完全不同：

```
「英伟达没了黄仁勋」
「英伟达第一次没有黄仁勋」
   → 字符相似度 0
```

试过两种传统方法都失败：

| 方法 | 结果 |
|---|---|
| 2 字词重合 | 误判 1400+ 对（「腾讯」和「黄仁勋」被判重复） |
| 4 字词组重合 | 漏掉所有改写，真重复被判不重复 |

**最终方案**：把当天候选标题交给模型做语义分组，同组只保留分数最高的那条。

- 每天调用 2 次（出刊 + 速览各一次）
- 成本约 0.01 元
- 模型失败就不去重，不影响出刊

### 8.6 对话：省钱 + 不卡住

```
用户点展示问题
   ↓
后端查 articles.answers 里有没有这条问题的预生成答案
   ├─ 有 → 直接返回（0 调用），但**照常扣一次额度**
   └─ 没有 → 调模型（带文章正文 + 最近 6 条对话）
```

**为什么扣额度**：体验上必须一致，用户不知道哪些是缓存、哪些是实时生成。

**防卡住的三道保险：**

| 问题 | 解法 |
|---|---|
| 推理模型把 token 花在思考上，返回空 | `effort: 'low'` + `max_tokens: 6000` |
| 长对话历史撑爆上下文 | 只带最近 6 条、每条 600 字 |
| 还是空 | 自动重试一次（9000 预算、只带最后一个问题） |

### 8.7 主题驱动：一期只有一份顺序

**问题**：网页按分数排，公众号按贴合度排，两套逻辑各排各的，用户对比时发现顺序不一样。

**定案**：把排序提前到出刊时做一次，落库，三处共用。

```js
// 出刊后：8 篇 → 主题 + 贴合度 → 存 settings
const plan = await buildThemePlan(db, edition, rows);  // {title, theme, order:[ids]}
saveThemePlan(db, edition, plan);

// 网页：listArticles 按 order 排
// 公众号：buildWechatArticle 读 plan
// 邮件：send-daily-mail 读 plan（缺失时现场补生成）
```

**踩过的三个坑**：

| 坑 | 现象 | 修法 |
|---|---|---|
| 页面二次排序 | 接口顺序对，页面不对 | 首页 `useMemo` 不再按 score 排 |
| 邮件先发、计划后生成 | 邮件按分数排 | 发信前缺失就补生成 |
| 缓存里存 0 基索引又被当 1 基转换 | 顺序错位 | 区分 `normalizeOrder` 与 `sanitizeZeroBased` |

### 8.8 周更的选稿窗口

日更是「当天候选」，周更不能这么做，否则周五只剩周五的文章。

```sql
SELECT *, score * (1 - MIN(6, julianday('now') - julianday(fetched_at)) * 0.05) AS adj
FROM candidates
WHERE status = 'new' AND score >= 60
  AND fetched_at >= datetime('now', '-7 day')
ORDER BY adj DESC
```

**为什么要衰减**：7 天窗口会让周一的高分文章霸榜整周，每期都是同一批。每天扣 5%、最多扣 30%，既保留质量，又让新内容有机会。

### 8.9 公众号文案：主题驱动

```
8 篇 → 模型找共性 → 主题 → 用主题起标题
              ↓
        给每篇打「贴合度分数」0–100
              ↓
    按分数排序：贴主题的在前，游离的在后
```

**为什么用分数而不是让模型直接给顺序**：让模型输出排列时，第一项经常错位；改成打分数再排序后稳定得多。

**生成结果示例：**

```
标题：结果还好看，长期代价已在累积
① 成绩没有下降 孩子却快撑不住了（最贴）
② 从资本密集到人力密集：全球AI的瓶颈
…
⑧ 环球徒步 28 年（游离，放最后）
```

排版全部用**内联样式**（公众号会剥掉 `<style>` 和 class）。

### 8.10 邮件订阅

```
提交邮箱 → 写入 pending + 生成两个 token（确认 / 退订）
        → 发确认邮件
用户点确认 → status = confirmed，从明天开始收信
每周五 19:03 → 查所有 confirmed → 逐个发（间隔 300ms）
```

**邮件正文只有三样东西**：

```
主题：Deepread 第 1 期
  [打开今天的 8 篇 →]
  ─────────────
  01 规则公平，差距为何仍会扩大？
  02 “柔性产能”：“中国制造”最硬的底牌
  …（8 条）
  ─────────────
  退订
```

**不放主题标题、不放主题总结、不放摘要**——这些需要人工校对后才能发公众号，邮件里只做提醒和导流。

**双重确认的必要性**：防别人乱填你邮箱、提高送达率、留下同意记录。

**防刷**：同一 IP 每小时最多 5 次提交。

### 8.11 本地存储（不用登录）

| 功能 | 存哪 | 过期 |
|---|---|---|
| 收藏 | `localStorage.dr_saved_v1` | 14 天自动清理 |
| 已读 | `localStorage.dr_read_v1` | 永久 |

**局限**：换设备、清缓存就丢。要跨设备只有登录一条路——但登录的摩擦比这个功能的价值大得多，所以 V1 不做。

**为什么收藏要有 7 天过期**：收藏夹很容易变成垃圾场。14 天自动清理 + 「已读完」按钮，让它只保留"你还没读的"。

### 8.12 埋点与指标

```
page_view      打开首页
article_click  点了哪篇（带分类和分数）
brief_click    点了哪条速览
question_click 点了哪个问题
chat_open      打开对话
chat_sent      发了一轮
next_click     点了 AI 的追问
chat_limit_hit 用满 3 轮
subscribe_*    订阅全流程
save_click     收藏
```

`npm run stats` 直接输出八个指标：

```
① 对话渗透率    打开对话 / 访问用户
② 饱和率        用满 3 轮 / 打开对话
③ 追问点击率    点追问 / 回答次数
④ 次日回访率    昨天用满今天又来
⑤ 收藏率        收藏 / 文章点击
⑥ 收藏读完率    点已读完 / 收藏
⑦ 订阅漏斗      提交 / 曝光
⑧ 订阅确认率    确认 / 提交
```

**踩过的坑**：`/api/track` 有一份事件白名单，收藏和订阅事件一开始不在名单里，全部被 400 丢弃——埋点写了，数据一直是空的。加新事件时**必须同时改白名单**。

**判读方法**：饱和率高 + 回访率高 = 真需求；只看饱和率会被好奇心骗。

## 十、已知限制

| 限制 | 影响 | 后续 |
|---|---|---|
| **没有域名** | 网址是 IP，记不住、分享不了 | 买域名 + 备案（2–3 周） |
| **没有 HTTPS** | 微信里提示不安全；剪贴板 API 受限；PWA 不可用 | 同上 |
| **163 发信限额** | 约 50 个订阅者上限 | 换腾讯云 SES / 阿里云（需域名） |
| **收藏不跨设备** | 换手机就丢 | 需要登录（暂不做） |
| **无人工复核** | 每期 8 篇完全自动，偶有偏题 | 可加"换一篇"按钮 |
| **周更触达低频** | 一周一次，早期用户容易被忘 | 视数据决定是否加周中提醒 |
| **只抓不存正文** | 原文失效后只剩摘要 | 合规取舍，不改 |

## 十二、术语表

| 术语 | 含义 |
|---|---|
