# Deepread 技术路线总结（截至 2026-11-08）

> 记录"实际做出来的东西"，方便和产品方案（v1.0 / v1.1）逐条对照。

## 一、一句话现状

一个能自动从 **295 个源**召回、用 DeepSeek 打**大众化**分、挑出值得读的长文的本地工具；线下可跑，线上有只读演示站。

---

## 二、数据流

```
295 个源（RSS + 列表页）
        │  npm run recall    并发抓取 · 去重 · 14 天时效 · 关键词拦截
        ▼
data/candidates.json     1026 条候选（标题 / 链接 / 来源 / 摘要）
        │  npm run rank      DeepSeek-V4.1-Flash 批量打分 0-100
        ▼
高分候选（≥70）
        │  点「收录」
        ▼
抓正文（Readability + 微信专用规则）→ 摘要 + 三个问题 → data/articles.json
        ▼
首页展示 / 点问题 → 和 DeepSeek 对话
```

## 三、模块清单

### 1. 召回（recall）

| 文件 | 作用 |
|---|---|
| `config/feeds.mjs` | 关键词黑名单、时效窗口（14 天） |
| `data/feeds.json` | 源注册表（295 个，可运行时增删） |
| `scripts/recall.mjs` | 并发抓取、HTML 清洗、去重、轮转排序、落库 |
| `lib/listpage.mjs` | 列表页抓标题（无 RSS 的站） |
| `lib/probe.mjs` | 探测一个地址是 RSS 还是列表页 |
| `scripts/import-opml.mjs` | OPML 批量导入（按新鲜度过滤） |
| `scripts/probe.mjs` | 命令行探测工具 |

**两种源**：
- `rss`：标准订阅源，289 个
- `html`：列表页，抓页面里的文章链接，6 个（界面新闻等）

**去重**：URL 归一化（去 utm）+ 标题归一化（去标点空格）。
**排序**：按源轮转，避免高频源刷屏。

### 2. 精排（rank）

| 文件 | 作用 |
|---|---|
| `scripts/rank.mjs` | 12 条一批、4 并发调 DeepSeek，写回 score / reason |
| `app/api/candidates/*` | 候选池读写、收录、丢弃 |
| `app/recall/page.tsx` | 审阅页：分数、筛选、源管理 |

**评分标准**（写在 prompt 里）：大众可读、讲清具体问题、有作者判断、10 分钟阅读量。
**明确扣分**：源码解析 / 架构设计 / 运维部署 / 框架对比 / 故障排查 → 不超过 55 分。

### 3. 收录（promote）

| 文件 | 作用 |
|---|---|
| `lib/extract.mjs` | 正文提取：Readability + jsdom，微信专用分支，403 cookie 重试 |
| `lib/llm.ts` | 摘要 + 三个问题（JSON 模式 + 长度校验） |
| `lib/store.ts` | 文章库读写、去重、分类、标题模式 |

**标题模式**：只抓标题和字数，不调模型（用于付费墙/无 RSS 的媒体）。
**降级**：抓不到正文 → `meta_only` 灰卡，仍然入库。

### 4. 展示与对话

| 文件 | 作用 |
|---|---|
| `app/page.tsx` | 今日列表：分类、摘要、三个问题、只收标题开关 |
| `components/ChatPanel.tsx` | 右侧对话面板（桌面）/ 底部抽屉（手机） |
| `lib/chat.ts` | 按需重抓正文，内存缓存 30 分钟 |

**对话**只基于正文回答，不允许编造；回复控制在 150 字以内。

### 5. 部署

| 项 | 现状 |
|---|---|
| 平台 | 腾讯云 CloudBase 云托管（容器，上海） |
| 域名 | `deepread-xxxx.sh.run.tcloudbase.com` |
| 模式 | `READONLY=1` 只读，禁止增删改 |
| 中间页 | 默认域名有「访问提示」，需点「确定访问」 |
| 数据 | 部署快照，线上不可写 |

## 四、关键技术决策

| 决策 | 原因 |
|---|---|
| **不存正文** | 只存标题、摘要、问题、300 字摘录；正文只在内存里过一遍 |
| **用 DeepSeek 而非 Jev** | 已充值、接口稳定、JSON 模式可靠，不必再引一套依赖 |
| **不用 RSSHub** | 成本高、稳定性差（早在 v1.1 方案里已删） |
| **RSS + 列表页双通道** | 中文优质媒体基本不发 RSS，列表页补位 |
| **OPML 批量导入** | 个人博客是高质量来源，1500 个里筛出 276 个活的 |
| **打分看标题+摘要，不看全文** | 300 条全文抓取代价太大；粗筛够用 |
| **分数跟着条目走** | 重新召回不重复花钱打分 |
| **Vercel → CloudBase** | Vercel 在国内不可访问（实测超时） |

## 五、和产品方案对照

### v1.0 计划 vs 实际

| 方案 | 状态 | 说明 |
|---|---|---|
| W1 粘贴 + 抓取 + 列表 | ✅ 完成 | 后来加了分类、移除、状态标签 |
| W2 摘要 + 问题 | ✅ 完成 | 改为 3 个问题（原方案是 1 个） |
| 「看 AI 怎么答」 | ✅ 完成 | 升级成多轮对话 + 右侧面板 |
| Jev 自动分类 | ❌ 未做 | 分类仍是手动 |
| 每日 5 篇 | ⚠️ 部分 | 有召回池，但「今天选哪 5 篇」仍是人工 |
| 用户系统 | ❌ 未做 | v1.0 本来就不要 |

### v1.1 计划 vs 实际

| 方案 | 状态 | 说明 |
|---|---|---|
| 召回层（RSS + 播客 + 人工） | ⚠️ 部分 | RSS ✅、列表页 ✅、播客 ❌（要 ASR） |
| 粗排 → 精排 → 重排 | ⚠️ 部分 | 只做了精排（LLM 打分），没有粗排和重排 |
| 公众号自动召回 | ❌ 不可行 | 需微信登录态，第三方服务不稳定 |
| 每周长内容 | ❌ 未做 | |
| 财报横评 | ❌ 未做 | |

### 方案里没有、实际做出来的

- 列表页抓取（无 RSS 的站）
- OPML 批量导入 + 存活性检测
- 只收标题模式（付费墙媒体）
- 源管理界面（增删/停用/现场测试）
- 大众化评分标准（技术实战文压分）

## 六、已知问题与技术债

**架构层面**
1. **JSON 文件当数据库**：线上只读，写操作必须重新部署；多用户不可能
2. **没有定时任务**：`recall` 和 `rank` 要手动跑
3. **召回是单机脚本**：295 个源串行跑约 3 分钟，没有增量机制

**内容层面**
4. **公众号只能手动**：无 RSS，微信不给接口
5. **付费墙媒体只能收标题**（三联实测只抓到 363/6507 字）
6. **跨源同题不合并**：同一事件多家报道会重复出现
7. **列表页抓取依赖页面结构**：站点改版就失效
8. **打分不看全文**：标题平平但内容好的文章会被漏掉

**体验层面**
9. **微信中间页**：需要备案域名才能去掉
10. **无失败重试**：抓取失败的文章要手动点「重试」

## 七、成本

| 动作 | 成本 |
|---|---|
| 全量排序（1026 条） | ≈ 0.4 元 |
| 单篇收录（抓正文 + 生成） | ≈ 0.01–0.02 元 |
| 一轮对话 | ≈ 0.01 元 |
| 每天增量排序（几十条） | 几分钱 |

## 八、运行方式

```bash
npm run dev            # 本地开发
npm run recall         # 召回（295 个源）
npm run rank           # 精排（只打没分过的）
npm run import-opml -- docs/feed.opml 人文   # 批量导入源
npm run fetch -- <url> # 单篇抓取
```

部署：`tcb cloudrun deploy --source ./deploy`（需要先打包 `deploy/` 目录）。
